# 0.1 engine validation report

These results describe the tested workloads and configurations. The
[support matrix](../compatibility.md) defines their support scope. They do not replace
[release acceptance](../release-acceptance.md) for the final packaged candidate.
The current support baseline is vLLM 0.30.0. Older results are retained under
[historical validation](#historical-validation-vllm-0260).

## vLLM 0.30.0 feature checks

The feature checks used two A100-SXM4-80GB GPUs on Linux x86-64. Tensor parallelism
used both GPUs; the other cases used one. Qwen2.5-0.5B-Instruct covered tensor
parallelism, LoRA, and offload. Qwen3.5-0.8B covered hybrid cache groups.
These checks used 288 successful requests derived from 12 public Mooncake conversation
trace rows, repeated three times per model or adapter. They preserved token counts
and shared prefixes, but did not reproduce the trace's arrival timing.

| Case | Captured and emitted block events |
| --- | ---: |
| Tensor parallelism 2 | 2,132 |
| Base model and LoRA adapter | 4,422 |
| CPU offload with placeholder events | 3,795 |
| CPU offload with self-describing events | 3,795 |
| CPU offload with 64-token chunks and 16-token GPU blocks | 3,072 |
| CPU and local filesystem offload | 4,424 |
| Hybrid cache groups 0–3 | 54 |

An independent subscriber captured the engine stream. Comparison with sealed Parquet
found no missing or extra block events and no sequence gaps. Independent recomputation
matched all 21,694 emitted content identities. Base-model and adapter content identities
were disjoint in this workload. No raw adapter-name or session-ID matches were found in
decoded records. This scoped check does not replace the privacy guarantees and exclusions
in [the trust document](../trust.md).

These are short correctness checks, not throughput or leak-soak measurements. They do
not validate every combination of parallelism, adapters, and offload. Deployment failure
checks are documented separately below.

## SGLang 0.5.20 feature checks

The checks used one A40 GPU on Linux x86-64 with the `lmsysorg/sglang:v0.5.20` image,
Qwen2.5-0.5B-Instruct, page size 16, and a 4,096-token cache so that evictions occurred.
An independent subscriber captured the publisher stream; the captures and the runbook are
in the specification repository under `capture/` with the `sglang-` prefix. The captured
bytes are the `sglang-wire` corpus's source, and the tap reproduces every fixture.

| Case | Messages | Captured block events |
| --- | ---: | ---: |
| Radix cache: reuse, split, salt, evictions, flush | 153 | 5,843 GPU stores, 5,595 GPU evictions, 1 clear |
| Hierarchical cache, host tier, write-through | 165 | 5,869 GPU and 4,167 host stores, 5,616 GPU and 3,675 host evictions |

The reuse check sent one 1,088-token prompt three times. The first request produced one
rooted store of 68 pages; the second and third produced no event. A prompt sharing the
first half of that prompt produced one store of 31 pages whose parent was a page of the
split node, and nothing for the shared half. Under the hierarchical cache, the first
request produced the GPU store and one host-tier store with the same hashes, and the
repeats produced nothing. The tap therefore declares `reuse_reporting: none` for SGLang.

The same prompt under two cache salts produced two rooted stores, each carrying its salt
at event level; the repeat under the first salt produced nothing, and the unsalted repeat
produced nothing because the unsalted prefix was already cached. A salted prompt sharing
half of a salted prefix produced a store with a parent and the salt, on both tiers.

`POST /flush_cache` produced one `AllBlocksCleared` in the next step's batch, scoped by
the batch's rank alone. Two prompts sent with no subscriber attached left a four-message
gap; a replay request from the last observed sequence returned those six messages and the
end marker, and a replay from zero returned all 160.

Every captured hash fit 64 bits and 5,932 of 11,438 hashes in the radix-cache capture
were negative, which is the engine's signed encoding of the same value. The tap reads a
negative hash as its unsigned value under the SGLang profile.

These checks used tensor parallelism 1 and one rank. Tensor-parallel widths above 1, data
parallelism, the `DISK` and `EXTERNAL` storage tiers, EAGLE speculative decoding, LoRA
adapters, and `session_id` attribution were not exercised. They are correctness checks
of the wire mapping, not throughput measurements.

## Additional lifecycle and edge checks

The same engine version and hardware were used for the following checks. Event collection
and content-identity completeness are separate results. A counted missing identity is
visible to consumers, but does not establish that the omission was unavoidable.

| Case | Result |
| --- | --- |
| Dynamic LoRA without offload | 60 requests and 3,522 block events; all content identities independently verified |
| Different adapter weights loaded under the same name | 36 requests and 1,718 block events; collection passed, but content identities do not distinguish the weight revisions |
| TP=2, dynamic LoRA, and placeholder CPU offload | 60 requests and 4,103 block events; all content identities independently verified |
| Cache salt with placeholder CPU offload | 36 requests and 3,795 block events; all content identities independently verified |
| Warm attachment with full replay | All 116 retained batches recovered; no missing content identities |
| Warm attachment without replay or with a two-batch replay buffer | Available events preserved; missing identities matched the omission counter |
| GPU cache reset and whole-engine restart | One clear and one holder reset matched the captured stream in order |
| Two local data-parallel ranks and whole-engine restart | 72 requests and 3,738 block events; order and present content identities independently verified |
| Hybrid boundary lengths, with and without CPU offload | Groups 0–3 and skipped-block spans collected; missing identities counted |
| Concurrent shared-prefix traffic | All 8,391 block events collected; independent replay verifies every identity |
| Two local filesystem tiers | Both tiers wrote blocks; all 6,212 block events collected, without distinct owner identifiers |

The object-store check used a loopback S3-compatible service. Stock vLLM 0.30.0 with
NIXL 1.4.1 failed with `NIXL_ERR_NO_TELEMETRY`, including without the tap. Its object-store
manager reads transfer telemetry but creates its NIXL agent without enabling capture.
Enabling `capture_telemetry=True` in that manager allowed 48 requests and 5,753 block
events to pass, including a five-second service pause. Transfer metrics confirmed reads
and writes. This is evidence for a locally patched engine, not stock-engine support or
validation against AWS S3. A separate AWS check is documented below.

## Four-GPU tensor parallelism

The TP=4 checks used four T4 GPUs, vLLM 0.30.0, and Qwen2.5-1.5B-Instruct in FP16.
The base model revision was `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`.
The dynamic adapter was `jfranklin-foundry/Qwen-Qwen2.5-1.5B-Instruct-1727463626`
at revision `8ebe62eeeeded1bdf928a47c2411b95a92da37f1`.

| Case | Successful requests | Captured and emitted block events |
| --- | ---: | ---: |
| GPU cache reset and whole-engine restart | 60 | 2,806 |
| Dynamic LoRA, shared prefixes, and self-describing CPU offload | 216 | 20,149 |

Neither case had request errors, missing or extra block events, or omitted identities.
Independent calculations matched every content identity. Ordered comparison matched
block, parent, tier, cache-group, locality, and cache-spec fields, along with the clear
and holder-reset records in the restart case.
The combined case exercised adapter load, unload, and reload and emitted 9,277 GPU
and 10,872 CPU block events. Base and adapter content identities were disjoint.
No raw adapter-name or session-ID matches appeared in decoded records.

These are correctness checks for the tested four-GPU configuration, not throughput
measurements or evidence for other tensor-parallel widths.

same model families and public trace rows. The six cases completed 375 requests

| Case | Block events | Independently verified content identities |

## Bounded-state validation

A one-hour GPU run on one A10G completed 5,077 requests without errors and collected
419,880 block events. Ordered comparison and independent identity calculations matched
every event, with no missing or extra events, sequence gaps, or omitted identities.
The workload used public Mooncake trace lengths and shared prefixes with 32 clients.
The engine used vLLM 0.30.0 and Qwen2.5-0.5B-Instruct.

KV utilization reached 100% of the configured 160 GPU blocks, with 1,085 preemptions.
This deliberately reduced cache capacity exercised eviction pressure; it did not fill
physical GPU memory. Tap RSS peaked at 9.32 MiB and remained steady during the run.
The bridge retained 158 entries at shutdown. The 29.37 MiB spool retained all output
for comparison under a 2 GiB cap, so this run did not exercise retention pressure.

A ten-minute GPU offload run completed 2,736 requests and 168,951 block events.
Ordered comparison and independent identity calculations matched every event, with no
sequence gaps or omitted identities. Tap RSS peaked at 8.64 MiB and the bridge retained
379 entries at shutdown. Sampled KV utilization peaked at 64.6%, with no preemptions.
This run exercised repeated offload traffic, not full KV capacity. Its 12.86 MiB spool
remained below the configured 64 MiB cap and did not exercise retention pressure.

A five-minute local live-transport run submitted and collected 4,820,000 block events
without sequence gaps. The publisher sent unique stores without matching evictions to
exercise capacity refusal. The bridge stayed at its configured 10,000-entry cap and
reported 4,810,000 refusals. Peak process RSS was 51.2 MiB under a 256 MiB budget.
Total spool use peaked at 8.53 MiB with an 8 MiB retention cap; active segment conversion
accounts for storage outside the retained-file cap. These finite observations complement
the entry and scope bounds; they do not establish a universal RSS ceiling.

## Kubernetes deployment checks

Kubernetes examples attach to an engine managed by the operator. They do not provide
an engine controller. Distributed engine recovery may require restarting the whole
engine group; a healthy coordinator endpoint does not prove that every rank serves
requests. See the [Kubernetes deployment guide](../../packaging/kubernetes/README.md).

### vLLM 0.30.0, single GPU

The packaged tap and shipper ran beside vLLM 0.30.0 on one A10G GPU under Restricted
Pod Security on K3s v1.36.4+k3s1. The engine used Qwen2.5-0.5B-Instruct. The baseline
and fault workloads completed 282 requests without errors.

The checks killed the tap, shipper, and engine containers separately. Serving recovered
after engine restart. An independent probe confirmed that NetworkPolicy blocked access
to the test object store during the shipping outage and allowed access after recovery.
An unrelated pod could reach inference but not the publisher or replay ports.

The final shipped output contained 24,642 store records, a segment-recovery record, and
a holder-reset record. Graceful pod termination took 2.97 seconds and delivered the
final tap stop record. This checks lifecycle and shipping; the workload did not fill
the KV cache or retention ring.

### vLLM 0.30.0, two local data-parallel ranks

The packaged tap and shipper ran with two T4 GPUs in one engine pod on K3s
v1.36.4+k3s1 under Restricted Pod Security. The engine used Qwen2.5-0.5B-Instruct
in FP16, data parallelism 2, and tensor parallelism 1. Baseline and fault workloads
completed 213 requests without errors, with requests directed to both ranks.

The checks covered tap and shipper crashes, whole-engine container restart, publisher
and replay isolation, and a shipping outage. An independent probe confirmed that
NetworkPolicy blocked storage access during the outage and restored it afterward.
Final output contained 19,473 store records across both ranks, one segment-recovery
record, and two holder-reset records. Graceful termination took 2.81 seconds and
delivered the final stop record. This checks lifecycle and shipping, not KV saturation
or disk retention pressure.

### vLLM 0.30.0, two data-parallel pods on one node

Two engine pods each used one T4 GPU on the same K3s node, with the same model,
engine version, FP16 precision, and Restricted Pod Security settings as the local-rank
check. Baseline and fault workloads completed 213 requests without errors.

An unrelated pod could reach inference but could not read either rank's publisher or
replay ports. Each engine pod was also unable to read the other rank's event ports.
The checks covered tap and shipper crashes, coordinated restart of both engine
containers, and a shipping outage with independently verified denial and restoration.

Final output contained 17,705 store records across both ranks, one segment-recovery
record, and two holder-reset records. Graceful shutdown took 3.22 seconds and delivered
both final stop records. Cross-node operation on vLLM 0.30.0 is expected to preserve
the tap behavior because each tap reads its local engine publisher. Cross-node
recovery was exercised on 0.26.0; it was not repeated on 0.30.0.

## Native ARM64 checks

The release build and `cargo test --all-features --locked`, including doctests, passed
on Linux ARM64 on a Graviton2 host: 305 tests passed and none failed. The directory-lock
subprocess fixture remained explicitly ignored as a standalone test. The suite ran as
an unprivileged user so permission checks exercised file-mode enforcement.

Colocated GPU integration could not start on the host's T4G GPU. The tested official
vLLM 0.30.0 ARM64 images lacked CUDA kernels for its SM75 architecture.
The default image used PyTorch 2.13.0; the `v0.30.0-cu129` image reported PyTorch 2.14.0. CUDA execution failed before tap
attachment. This establishes an incompatibility between
those engine images and T4G, not a tap incompatibility with ARM64 or newer GPUs.
Real GPU integration on ARM64 remains unvalidated.

## AWS S3 offload

The AWS check used one A10G GPU, Qwen2.5-0.5B-Instruct, vLLM 0.30.0, and NIXL 1.4.1.
The engine used 160 GPU blocks, a 32 MiB primary CPU tier, and an S3 secondary tier.
The workload derived token counts and shared prefixes from public Mooncake trace rows.

Stock vLLM failed with `NIXL_ERR_NO_TELEMETRY`. The following cases used the local
`capture_telemetry=True` engine patch described above. Both required
`ca_bundle=/etc/ssl/certs/ca-certificates.crt`; the backend's default CA path was absent
from the tested image.

| Case | Successful requests | Captured and emitted block events |
| --- | ---: | ---: |
| S3 offload and concurrent shared prefixes | 192 | 17,311 |
| Temporary S3 access denial and recovery | 72 | 8,852 |

Independent checks matched event order, tier and locality fields, and every emitted
content identity. Neither case had missing or extra events, sequence gaps, or request
errors. Engine tier counters confirmed S3 reads and writes. The fault case temporarily
denied object reads and writes, recorded failed transfer jobs, and continued serving
requests after access returned. This checks that access-denial scenario, not every
object-store or network failure. These results remain experimental because the stock
engine required a patch.

## Live backend ownership

The ownership check used one A10G GPU, Qwen2.5-0.5B-Instruct, vLLM 0.30.0, and
KVCR 0.1.0 from commit `317e62f301300c101bf9c911e020fb89b35f1583`, with its pinned
NIXL 1.3.2 dependency. The configuration used a 32 MiB primary CPU tier and a
128-slot KVCR local DRAM tier. It did not exercise remote peers or a Dynamo router.

All 216 requests succeeded. Independent comparison matched all 29,988 block events,
their order and fields, and every emitted content identity. The engine emitted 4,434
stores and 4,306 evictions with `ownership="kvcr"`. Each carried the expected
pseudonymized `backend_id`. Primary CPU events omitted ownership and retained a separate
scope. No raw owner-label matches appeared in decoded records.

This establishes live propagation and pseudonymization of one named backend alongside
an unowned tier. Multiple distinct named backends within one tier remain unvalidated.

## Stock object-store check with NIXL 1.3.2

Stock vLLM 0.30.0 also failed with `NIXL_ERR_NO_TELEMETRY` against a local S3-compatible
service with NIXL 1.3.2. The tap collected the events emitted before the engine failure.
Changing between the two tested NIXL versions did not remove the need for the engine's
telemetry initialization fix. This does not establish behavior on other versions.

## Historical validation: vLLM 0.26.0

These results record earlier test coverage. They are not tests of vLLM 0.30.0 and do
not establish a supported range of engine versions.

The single-pod check used two A10G GPUs with data parallelism 2 and tensor parallelism 1.
It covered tap and shipper crashes, a whole-engine container restart, an object-store
outage, and graceful shutdown under Restricted Pod Security. Both ranks emitted readable
Parquet records. This deployment check did not fill the KV cache or the retention ring.

A separate two-node data-parallel deployment exercised both ranks, event-port isolation,
shipping, and coordinated engine-group recovery.

The official 0.26.0 ARM64 image used PyTorch 2.11.0 and also lacked SM75 kernels for
T4G. CUDA execution failed before tap attachment.
